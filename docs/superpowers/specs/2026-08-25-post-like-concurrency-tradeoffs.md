# 좋아요 동시성 — 접근법 트레이드오프 비교

작성일: 2026-08-25
상태: 브레인스토밍 중간 산출물 (설계 확정 전 근거 자료)

## 배경 / 문제 정의

- **관심 시나리오:** 서로 다른 사용자가 거의 동시에 같은 글에 좋아요 → 좋아요 수가 `+2`가 아니라 `+1`만 반영되는 **lost update** 예방.
- **현재 구조 (중요):** 좋아요 수는 저장된 카운터가 아니라, 매 조회 시 `postLikeRepository.countByPostId(id)` = `SELECT COUNT(*) FROM post_like WHERE post_id=?` 로 집계된다.
  - `post_like(post_id)` 인덱스 존재 → 인덱스 레인지 카운트.
  - `uq_post_like UNIQUE(post_id, member_id)` 존재 → 사용자별 중복 행 불가.
- **따라서 현재 코드에는 lost update가 존재하지 않는다.** 사용자 A·B가 각자 별도 행을 INSERT할 뿐이라 `COUNT(*)`는 항상 정확히 `+2`. Redis 인기점수도 `ZINCRBY`(원자적)라 안전.
- **진짜 동기:** 조회 시 매번 `COUNT(*)` 집계가 응답 속도에 손해라는 우려 → 좋아요 수를 **컬럼으로 비정규화**하려는 것. 비정규화를 하는 **순간에** lost update 문제가 새로 생기며, 그것을 어떤 방식으로 막을지가 본 문서의 비교 대상이다.

> ⚠️ 전제 리스크: "COUNT(*)가 느리다"는 아직 **측정된 사실이 아니라 가정**이다. 인덱스가 있어 일반 글은 sub-ms, 바이럴 글에서만 수 ms 수준. 측정 없이 비정규화로 진행하기로 한 결정이므로, 훗날 "COUNT가 실제 병목이었나?"를 되짚을 근거로 이 전제를 명시해 둔다.

## 비교 축

| 축 | 의미 |
|---|---|
| 정확성 | 동시 증감에서 lost update를 막는가 |
| 처리량 | 같은 글 동시 좋아요 시 직렬화/경합 정도 |
| 복잡도 | 코드·운영·장애 대응 부담 |
| 인프라 의존 | write 경로에 새 실패 지점을 추가하는가 |
| 정합성 리스크 | DB 실제 상태와 카운터가 어긋날 여지 |

## ① 원자적 SQL 증감 — **권장**

`UPDATE post SET like_count = like_count + 1 WHERE id = ?` (취소는 `- 1`). 좋아요 행 INSERT/DELETE와 **같은 트랜잭션**에서 실행.

- **정확성:** DB가 해당 행에 배타 락을 걸고 read-modify-write를 원자적으로 처리 → 동시 N요청이 정확히 `+N`. lost update 원천 차단.
- **처리량:** 락은 단일 행·단일 문장 수준으로 매우 짧게만 유지 → 실질 경합 미미.
- **복잡도:** 가장 낮음. 앱은 락을 인지할 필요 없음. 재시도 로직 불필요.
- **인프라 의존:** 없음 (기존 DB 트랜잭션만 사용).
- **정합성 리스크:** 행 INSERT/DELETE와 카운터 증감이 한 트랜잭션이라 함께 커밋/롤백 → `post_like` 행 수와 `like_count`가 어긋나지 않음.
- **주의점(구현 위임):** 벌크 `UPDATE`(JPQL `@Modifying`)는 영속성 컨텍스트의 엔티티를 갱신하지 않아, 직후 `post.getLikeCount()`가 stale일 수 있다 → `promoteIfPopular` 임계값 판정을 이 stale 값으로 하지 않도록 처리 필요. (구현 방식은 tdd-team에 위임)

## ② 낙관적 락 (`@Version`)

엔티티를 읽어 `likeCount + 1` 후 저장, 버전 충돌 시 예외 → 재시도.

- **정확성:** 재시도까지 포함하면 보장.
- **처리량:** 좋아요는 인기 글에서 동시성이 높은 카운터 → **버전 충돌·재시도 폭풍**이 나기 쉬움. 경합이 셀수록 재시도로 낭비.
- **복잡도:** 재시도 루프/예외 처리 필요. `@Version`을 `Post`에 붙이면 좋아요뿐 아니라 **제목 수정·조회수 등 Post의 모든 write 경로**가 버전 검사 대상이 되는 광범위한 부작용.
- **인프라 의존:** 없음.
- **정합성 리스크:** 낮음.
- **평가:** 카운터 하나 때문에 엔티티 전역에 낙관적 락을 도입하는 것은 과함. 경합 높은 카운터에는 특히 불리.

## ③ 비관적 락 (`SELECT … FOR UPDATE`)

좋아요 처리 전에 `post` 행을 배타 락으로 선점.

- **정확성:** 보장.
- **처리량:** 같은 글의 좋아요 요청을 **완전 직렬화** → 인기 글일수록 처리량 최악, 락 대기·타임아웃 위험.
- **복잡도:** 중간. 트랜잭션 경계·락 순서 주의 필요(데드락 여지).
- **인프라 의존:** 없음.
- **정합성 리스크:** 낮음.
- **평가:** ①이 이미 원자성을 주므로 굳이 더 무겁게 직렬화할 이유가 없음. 이 문제엔 불필요.

## ④ Redis 분산 락 (요청 반영)

좋아요 처리 구간을 Redis 락(`SETNX`+TTL, 또는 Redisson/Redlock)으로 상호배제.

- **정확성:** 락이 정상 동작하면 보장. 단 **TTL 만료·프로세스 지연·클럭 스큐** 시 두 요청이 동시에 임계구역 진입 가능 → 분산 락은 근본적으로 "완벽한 상호배제"를 보장하지 못한다(Redlock 안전성 논쟁). 결국 **최종 정합성은 DB 제약/원자 연산에 다시 의존**해야 함.
- **처리량:** 락 키를 글 단위(`lock:post:like:{postId}`)로 잡으면 같은 글 좋아요가 직렬화 → ③과 유사하게 인기 글에서 병목. 게다가 매 요청 **Redis 왕복(획득+해제)** 추가로 지연 증가.
- **복잡도:** 가장 높음. 락 획득 실패 시 대기/재시도/포기 정책, TTL 산정, 락 해제 보장(토큰 기반 안전 해제), 락 재진입, 예외 시 누수 방지 등 운영 난이도 큼.
- **인프라 의존:** **write 경로에 Redis를 강한 의존으로 추가**. 현재 Redis는 캐시·인기점수 용도로 **graceful degrade**(장애 시 무시) 설계인데, 분산 락은 장애 시 무시하면 상호배제가 깨지므로 degrade가 불가 → Redis 장애가 좋아요 쓰기 장애로 전파.
- **정합성 리스크:** 락과 DB가 별개 시스템이라, 락은 잡혔는데 DB 커밋이 실패/롤백되는 조합 등 **이중 시스템 정합성** 관리 부담.
- **평가:** **명백한 오버엔지니어링.** 분산 락은 "여러 노드가 DB로 표현 불가능한 공유 자원을 조율"할 때 쓰는 도구다. 여기서 조율 대상은 **단일 DB 행의 숫자 하나**이고, 그 원자성은 DB가 이미 `UPDATE ... +1`로 공짜로 제공한다. 락을 얹으면 더 느리고, 더 복잡하고, 새 장애 지점이 생기며, 그래도 최종 정합성은 결국 DB에 의존한다. 프로젝트 가이드("측정된 병목 없이 인프라 선제 적용 금지")에도 정면으로 어긋남.

## 결론

- 채택: **① 원자적 SQL 증감** (`UPDATE post SET like_count = like_count ± 1`), 좋아요 행 변경과 동일 트랜잭션.
- lost update 방지에 **락 계열(②③④)은 전부 불필요**하며, 특히 ④ Redis 분산 락은 이 문제엔 비용·복잡도·장애 위험이 가장 큰 부적합 선택.
- 남은 구현 논점(비정규화 컬럼 도입·백필, `promoteIfPopular`의 stale 값 처리, 읽기 경로에서 COUNT 제거)은 후속 설계 문서에서 다룬다.
